# Compatibility decisions and proposals

**Status: the performance budget, Safari exclusion and estimated browser-version floors below are adopted decisions. Test execution and compatibility must be verified separately.**

## Required performance floor

As of 12 September 2026, use **Lighthouse BenchmarkIndex 264** as this project's estimated fifth-percentile phone CPU floor. Fixed metrics live in [`performance-budget.json`](../performance-budget.json). Higher scores indicate faster performance.

This is an engineering estimate, not a measured percentile of active phones. The anchor is [Chrome DevTools' low-tier calibration score](https://chromium.googlesource.com/devtools/devtools-frontend/+/HEAD/front_end/panels/mobile_throttling/CalibrationController.ts), which uses 264. That source does not establish a population percentile. We adopt its low-tier reference as a practical planning proxy because it can be reproduced across development machines. Phone age, RAM capacity and advertised CPU frequency cannot provide an equivalent JavaScript speed target. Confidence in the fifth-percentile interpretation is low. Keep the number fixed until an explicitly reviewed policy change rather than silently following upstream changes.

At this floor, **no application-owned synchronous main-thread task may exceed 1000 / 60 ms (approximately 16.67 ms)**. Initialization, hydration, event handlers, their microtask checkpoints, animation callbacks, resize handling and cleanup count. Framework/dependency work serving the application also counts. Several short tasks can exhaust a frame: target at most **10 ms of combined application work per frame**, leaving rendering headroom. This target does not replace the hard task limit. [Rendering guidance](https://web.dev/articles/rendering-performance) explains why JavaScript cannot consume the entire frame budget.

An animation or asynchronous operation can span many frames; its individual blocking work must meet the budget. Network waiting and total animation duration need not fit inside one frame. Synchronous layout or paint caused by application code counts in the task. Browser scheduling, GPU completion and display presentation affect visible smoothness too: passing CPU timings alone does not prove uninterrupted 60 fps.

Preserve artwork, density, motion feel and interactions. Reduce repeated work and allocation before adding complexity; split expensive work where behavior permits. Do not meet the budget by lowering quality or weakening thresholds. Less CPU work benefits faster phones too, although energy savings and FPS improvements require separate measurement.

## Suggested verification procedure and current status

1. Build and locally serve the production static application. Use a foreground Chrome tab on a quiet machine at all three required viewport sizes. Record browser version, host hardware, viewport and device pixel ratio.
2. Calibrate throttling to BenchmarkIndex 264 using DevTools' low-tier mobile preset. Confirm the installed DevTools still targets 264; otherwise calibrate explicitly against the stored score. Record achieved score and multiplier. A score within 10 points is the cited implementation's calibration tolerance, not a population confidence interval. A generic 4x or 6x slowdown is not equivalent across machines. See [DevTools calibration guidance](https://developer.chrome.com/blog/devtools-grounded-real-world).
3. Trace cold initialization, idle animation, continuous pointer movement, touch/re-entry recovery, scrolling, orientation/viewport changes, reduced motion, navigation and cleanup. Include first interaction and first frame, not only warmed-up rendering. Repeat scenarios three times, for at least 10 seconds where applicable.
4. Inspect the maximum application task duration and combined application work per frame. Any observed task over the stored maximum fails that scenario; averages or percentiles cannot hide it. Investigate instrumentation overhead or external interference with a fresh recording and retain the explanation rather than retrying until green. Report missed frames separately from JavaScript duration.

The JSON records requirements; it is **not an automated timing gate**. Existing tests check correctness and motion behavior. The refactor's uncalibrated desktop/4x measurements do not establish compliance with this new floor. Calibrated maximum-task acceptance remains **unverified**. A passing correctness suite is not a performance pass.

Future automated timing checks should use a dedicated calibrated job, separate from parallel correctness workers, with a stable runner/browser and recorded calibration. Fail or invalidate runs when the target cannot be reached. Shared-runner contention makes tight timing tests noisy. Measure application work through existing interfaces and browser traces; avoid a custom benchmark framework merely to assert constants.

## Browser compatibility

Safari is **not supported by this project**. Apple discontinued Safari for Windows and does not provide Safari for Linux. Our Windows development and Linux CI environments therefore cannot run current branded Safari locally. This is a project support decision, not a claim that Safari cannot work or cannot be automated on Apple platforms. Do not block Safari visitors or introduce browser detection because of this policy. [Apple platform availability](https://support.apple.com/en-ca/102665).

WebKit coverage is deferred to [issue #2: evaluate experimental WebKit coverage and browser-test tooling](https://github.com/Stegi56/Portfolio/issues/2). Cypress labels its WebKit integration experimental and uses Playwright WebKit underneath. WebKit is Safari's engine, but testing a WebKit build on Windows/Linux does not verify the Safari application, a particular iOS release, or native Apple-platform behavior. The issue covers dependencies, known runner limitations, existing Chrome-specific tests and a comparison with Playwright. No WebKit testing or Safari support is implied by the current suite. [Cypress WebKit documentation](https://docs.cypress.io/app/references/launching-browsers#webkit-experimental).

The estimated bottom-5% browser-version floors evaluated on **12 September 2026** are **Chrome 109, Firefox 115 and Edge 120**. Firefox 115 selects the older end of the estimated 115-120 range. The default browser test targets are **Chrome 109, Firefox 115 and Edge 120**, with exact platform-specific binaries in [`test-browsers.json`](../test-browsers.json). Firefox 115 launches with the selected compatible test runner, so no Firefox-version exception is currently needed. If a future runner cannot launch the estimated Firefox floor, use the oldest launchable version and try consecutive majors upward until launch succeeds; application test failures do not justify increasing the version. Re-evaluate on **12 March 2027**, six months later: [review issue #3](https://github.com/Stegi56/Portfolio/issues/3).

These estimates come from August 2026 identifiable numeric-version usage, normalized within each browser family. They are not fifth percentiles of unique people or phones: rounded shares, unknown/unversioned entries and platform classification limit the evidence. Treat them as fixed planning targets until the review, not a statistical 95% guarantee. [Usage source](https://gs.statcounter.com/browser-version-market-share/desktop/worldwide/#monthly-202608-202608-bar), [methodology](https://gs.statcounter.com/faq).

The targets apply to browser tests; pure motion tests continue to run in Node. Browser binaries must match the configured version rather than silently selecting a newer installed browser. A mobile viewport does not establish native mobile-browser coverage. Current Cypress releases support recent browsers; the selected legacy runner therefore requires explicit verification for these targets rather than an upstream support claim. Chrome 109 is also below the framework's documented Chrome 111 floor: passing application tests is needed to evaluate actual behavior, and framework support must not be claimed for it. [Cypress version support](https://docs.cypress.io/app/references/launching-browsers#browser-versions-supported), [Next.js support](https://nextjs.org/docs/app/getting-started/installation#supported-browsers).

The browser floor takes precedence over Baseline feature guidance. A feature meeting Baseline may still be unavailable in an older supported version; check the actual floor before adopting it. [Vite's Baseline policy](https://vite.dev/guide/build) is useful reference material, not this project's browser promise.

Basic content display when JavaScript is unavailable or fails is a backlog investigation in [issue #1](https://github.com/Stegi56/Portfolio/issues/1). A basic support tier or visual fallback has not been adopted. Preserve current appearance and motion until a separate proposal is approved.

GOV.UK's explicit browser coverage and usable-content principles inform the discussion, but its full operating-system/browser matrix is not adopted here. [GOV.UK compatibility guidance](https://www.gov.uk/service-manual/technology/designing-for-different-browsers-and-devices).

## Test toolchain and coverage

The browser defaults require **Cypress 14.5.4** and **TypeScript 5.9.2**, explicit exceptions to the dependency freshness rule. Cypress 16's own interface failed on Chrome 109 before the app loaded (`Promise.withResolvers` unavailable). Cypress 14's loader requires the JavaScript compiler API absent from TypeScript 7, and its preprocessor uses compiler options rejected by TypeScript 6. The pinned pair keeps one runner/compiler without altering application behavior to accommodate test tooling. Re-evaluate these exceptions in [issue #3](https://github.com/Stegi56/Portfolio/issues/3).

Chrome 109 uses its unified headless mode (`--headless=new`). Cypress 14 otherwise selects the older headless implementation, where the embedded application's smooth scrolling failed during local validation. The original contact navigation assertions remain in place. [Headless mode availability](https://www.selenium.dev/blog/2023/headless-is-going-away/).

**Edge remains unvalidated:** on the evaluated Windows machine, the genuine Edge 120.0.2210.121 executable crashes before application tests in its default headless mode (`0xC0000005`). Its old headless mode starts but does not create the initial page Cypress requires. The configured Edge floor is retained; local `npm test` still reports this failure. Linux Edge execution remains unverified. This is a test-launch failure, not evidence of an application assertion failure or authorization to raise the Edge version.

Under the user-approved temporary exception tracked in [issue #4](https://github.com/Stegi56/Portfolio/issues/4), CI runs Edge's Cypress step but permits that step to fail, with an explicit warning. Browser provisioning, Chrome, Firefox, unit tests, build and other setup remain blocking. Remove the allowance and warning when pinned Edge passes all 36 checks and three-size visual inspection. The exception is linked at its workflow definition and does not make Edge supported by verified evidence.

All shared browser tests run against each pinned browser. Two native touch/media checks use Chromium's debugging protocol and run on Chrome and Edge; Firefox reports these two explicitly as pending. Firefox's shared synthetic input and lifecycle checks do not establish equivalent native touch/media coverage. The runner validates actual browser product and version before testing; passing a newer system browser cannot satisfy these defaults.

Firefox 115's Windows headless screenshots currently omit the glass navigation's backdrop blur. Its headless mode disables hardware acceleration, but that alone does not establish the cause of this discrepancy. Passing layout and interaction checks does not establish full visual fidelity for this effect; keep this limitation explicit rather than changing application styling or forcing graphics preferences to obtain a passing screenshot. [Firefox 115 graphics initialization](https://github.com/mozilla/gecko-dev/blob/esr115/gfx/thebes/gfxPlatform.cpp).

Browser downloads are isolated under the ignored `.cache/test-browsers` directory and verified against stored SHA256 hashes. Linux Chrome 109 is extracted from a digest-pinned official Cypress browser image because its old package is no longer directly served by Google. Windows and Linux use different patch builds within Chrome 109, recorded in the manifest. Local Windows runs do not by themselves verify Linux CI execution. Browser tests do not establish compliance with the separately recorded calibrated CPU timing budget.
