# Portfolio project guidance

This file contains minimal context that cannot be inferred from the project itself.

- Keep `aws` selected when the skills state is first created. This is intentional: the initial highlighted skill teaches visitors that skill pills are interactive and can be selected.
- The project must remain a compiled static application that can be hosted on GitHub Pages.
- Navigation links to sections on the current page must use browser-native smooth scrolling. A section hash loaded from another page or a cold load must align instantly.
- All user-facing changes must be visually verified at mobile (375×812), tablet (768×1024), and desktop (1440×900). Layouts must remain usable without horizontal overflow, clipping, overlap, or cramped content; automated visibility checks alone are insufficient.
- Pin npm dependencies to the latest stable major and minor release, one published patch behind the latest. Use the latest patch when no earlier patch exists in that release line or when a critical vulnerability affects the buffered patch.
- When dependencies or features are removed, clean up files and resources that are no longer used, and keep `.gitignore` current with generated artifacts.
- Validate changes locally. Do not deploy to GitHub Pages, publish the site, or otherwise trigger a production deployment without the user's explicit permission.
- Stage changes on a separate branch for the user to review. Only the user may merge that branch, with their explicit approval; agents must not merge it.
- Define system behavior and requirements in tests that exercise observable outcomes through module interfaces. Avoid tests coupled to private implementation details; obtain reviewer approval before changing existing behavioral coverage during a refactor.
- Remove temporary briefs, review reports, and verification artifacts when the work is complete; keep enduring requirements in tests and project guidance.
- Optimize for low-end mobile hardware and junior maintainers: use descriptive names and straightforward control flow, remove repeated work before adding complexity, and support performance claims with measurements.
- Follow the performance budget in `performance-budget.json` (see adopted decisions and pending proposals in `docs/compatibility.md`): use Lighthouse BenchmarkIndex 264 as the explicitly estimated fifth-percentile phone CPU floor. At that floor, no application-owned synchronous main-thread task may exceed one 60 Hz frame (1000 / 60 ms); target at most 10 ms of combined application work per frame to leave rendering headroom. Preserve appearance and motion. Report unmeasured performance or browser compatibility as unverified; correctness tests alone do not establish timing compliance.

- Safari is outside the project's supported browser scope because current Safari is unavailable on Windows/Linux (Apple discontinued the Windows version; no Linux version is provided). Experimental WebKit coverage is deferred to https://github.com/Stegi56/Portfolio/issues/2; WebKit testing must not be presented as actual Safari coverage. This policy does not authorize blocking Safari visitors.
- Use the pinned Chrome 109, Firefox 115 and Edge 120 defaults in `test-browsers.json` for browser tests. These are estimated bottom-5% version floors evaluated on 2026-09-12, not measured population percentiles. Re-evaluate on 2027-03-12 under https://github.com/Stegi56/Portfolio/issues/3. If the estimated Firefox version cannot launch, use the oldest launchable version, trying consecutive majors upward; application test failures do not justify increasing it. Do not silently substitute newer installed browsers. The browser floor takes precedence over Baseline guidance.
- Attribute AI-created or AI-maintained GitHub issues with a label and body footer in the form `<actual AI model> on behalf of Joel Staugaitis` (for example, `gpt-6 on behalf of Joel Staugaitis`). Use the actual known model identity; do not guess a variant. Preserve existing attribution when another model contributes and add its own attribution as appropriate.
- Temporarily allow only the Edge Cypress execution step to fail in CI under https://github.com/Stegi56/Portfolio/issues/4; provisioning and other checks remain blocking, and local commands must report failures. Remove this allowance once the issue's validation criteria pass. Link temporary exceptions to their tracking issues directly where they are implemented.

- Compatibility exception to the dependency freshness rule: keep Cypress 14.5.4 and TypeScript 5.9.2 pinned for the requested old browser defaults. Newer toolchains failed before application tests could run. Revisit both pins with browser review issue #3; preserve one test runner and compiler rather than introducing compatibility shims into the application.
